# ADR 0027: SupplyConnect party records and explicit access

> **2026-10-23, #1287:** Pakistan was removed; India is the only supported country.

Date: 2026-10-16. Status: implementation in progress. Stories #1135, #1137 and #1005; network contracts follow #1136.

Use ADR 0026's planning targets (100 organisations, 300 operating locations, 100 peak API requests/s, 32 KiB bounded synchronous bodies, 99.9% availability and p99 500 ms reads). At 500 supplier records per tenant, 100 tenants hold 50,000 profiles; at 2x annual tenant growth, year three holds 200,000 profiles. Contact/address/registration arrays are bounded to 20 entries and stored in relational child tables. Pagination is by `(created_at,id)`, maximum 100. These are sizing assumptions, not measured capacity. The shared PostgreSQL/outbox/worker budget remains ADR 0026's unpriced USD 300–1,000/month allowance; this module adds no deployable or datastore.

SupplyConnect owns the single supplier/counterparty master. Its tenant-private business profiles distinguish an owned organisation from an offline/external counterparty; neither creates a tenant or an identity-provider organisation. Platform/Zitadel tenant identity remains authoritative. A typed external tenant ID cannot verify a network identity or grant trading authority. Future verified network references arrive through approved Platform contracts. Pharmacy ownership, hospital affiliations and common corporate groups grant no supplier data access.

A profile captures legal/trading names, code, business kind, ownership description, country, business registration, corporate group, website and commercial credit-day preference. Structured contacts, addresses and tax registrations are private children, never embedded in directory summaries or broker payloads. Country identifiers remain declared until checked against approved policy. Bank processing is outside initial reconciliation: repeatable masked bank/destination metadata and released evidence can be added with finance-specific access; raw account numbers/provider secrets must not enter generic profiles or audit payloads.

Global supply roles and permissions are necessary but insufficient. Explicit per-party roles determine read/edit/compliance/finance/warehouse/sales/audit access. New profile creation atomically records the creator's administrator grant; it never grants access to another existing profile. Tenant administrators can discover bounded directory headers and administer explicit grants, but private details still require a current object grant. Auditors are read-only; purchasing cannot approve licences; warehouse, sales and driver roles cannot read private legal/financial profiles. Revocation is checked against PostgreSQL on every request, not a stale session or cache. RLS enforces strict current tenant and party context; scoped child keys and foreign keys prevent mixed-tenant/party references.

Stable UUIDv7 aggregate IDs plus expected versions govern idempotent writes. Identical retries return the persisted database timestamps and do not create another revision, audit mutation or outbox event. Conflicting versions or business keys return 409. Profile edits retain immutable revisions and actor attribution. Legal approval/suspension/offboarding and licence review are separate versioned transitions; creating or editing identity never approves trading. Human review requires current, clean, generation-pinned evidence and an approved country/premises/category policy. OCR extraction is not verification. Maker/checker separation applies to approvals.

Business rows, grants, immutable history, audit and minimized NATS outbox intent commit in one PostgreSQL transaction. NATS failure leaves intent pending. Database/authorization/policy failure denies reads or commitments; Valkey is not an authorization source. Temporal and the existing GCS/ClamAV primitives are used for evidence processing, approval waits and renewal reminders as those workflows are implemented. Provider calls never run under database locks. No patient-level data is required.

Migrations are additive and forward-only, with bounded DDL timeouts and explicit `ON DELETE RESTRICT` references. Application rollback preserves profile/history records; it does not delete business data. Live migration/rollout is separately authorized through GitOps. Backups and restore targets remain RPO ≤5 min / RTO ≤60 min planning requirements awaiting production proof.

Reject a duplicate pharmacy vendor master or a fake hospital for a distributor: both introduce conflicting ownership and sharing rules. Reject a new service for supplier CRUD: there is no distinct scaling or failure-domain requirement. Reject implicit corporate-group access and public supplier contact data. The modular SupplyConnect implementation with explicit published references is the smallest design that preserves the target product API boundary.

## Implemented draft-profile slice

The current routes are `GET/PUT /v1/supply/parties/:party`, paged `GET /v1/supply/parties?q=<literal-prefix>`, paged `GET /v1/supply/parties/:party/revisions`, current-user `GET /v1/supply/parties/:party/access`, and administrator `PUT/DELETE /v1/supply/parties/:party/access/:subject/:role`. Directory access requires `supply.directory.read` and a current object grant, or grant-management permission for header discovery. Private profile/history reads additionally require `supply.party.read` and a current private-reading role. Writes require `supply.party.write` and administrator/purchasing scope; owned organisations additionally require `supply.organization.manage`. Grant changes require `supply.party.access.manage` and a profile visible within the active tenant. None of these routes approve licences or enable transactions.

The `/supply/parties` screen uses the real API, tenant-and-subject query keys, the shared dropdown/form controls, field-level validation, stable UUIDv7 input identities, explicit empty/error states, paged directory/history and automatic form focus. Tax declaration choices are generated from the same country metadata consumed by Go. A draft cannot change its country or owned/counterparty identity. Private contacts, addresses and tax declarations never appear in directory summaries. These are declared identifiers, not statutory validation or a claim of SOC 2/HIPAA certification.

Synthetic local acceptance created a counterparty with contact/address/tax metadata, updated it to revision 2 and verified persistence after browser reload. Browser validation also checks 390px responsive rendering, reusable tax/country dropdowns and console errors. Local test authentication is held outside tracked source and never enters a published image.

The remainder of #1135/#1005 includes premises/warehouse structure, scoped bank-destination metadata, secure evidence upload, licence verification and approval/suspension/offboarding. #1137 still needs complete workflow-specific roles/access administration and acceptance for later transaction domains. Those stories stay open; a private draft profile does not satisfy their full scope.
