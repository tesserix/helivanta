## Read contract and safe meaning

The existing hierarchy is `tenant → pharmacy organisation → outlet → location/lot`. Shared ownership or a hospital affiliation never grants stock access. Additive reads use `R = /pharmacy/pharmacies/{pharmacy}/outlets/{outlet}/stock` through the existing API client:

| Read                   | Contract                                                                                                                                                                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET R/positions`      | Required RFC3339 `as_of`; optional `location_id`, `product_id`, `expiry=all\|expired\|unexpired`; shared keyset cursor, default 50/max 200. Return recorded location/lot buckets, including zero balances after correction. A bucket with no movements is absent. |
| `GET R/reconciliation` | Exact owned `location_id` and `batch_id`, required `as_of`, optional `from` (defaults to 1970-01-01 UTC). One aggregate statement returns opening, receipts, signed corrections, closing and period movement count.                                               |
| `GET R/movements`      | Existing paginated immutable history gains matching `from`/`as_of` filters; source reference, reason, actor and recorded timestamp remain attributable.                                                                                                           |

Times normalise to UTC with at most microsecond precision; finer precision, malformed/reversed periods and future cutoffs are rejected. Future cutoffs are checked against the PostgreSQL clock, which is also the ledger timestamp authority; local tests exposed approximately 44 ms of host/database clock skew. Opening uses `created_at < from`; activity uses `from <= created_at <= as_of`; closing uses `created_at <= as_of`. Thus `opening + receipts + signed corrections = closing` for the two currently supported movement kinds. Quantities use integer base units, never floating-point arithmetic or sums across incompatible products/units. Cumulative receipt and signed-correction totals are decimal strings to avoid JavaScript precision loss; bounded on-hand/opening/closing remain integers. Duplicate receipt retries retain the existing unique source/idempotent write behaviour.

Current fields are product ID/SKU/name/unit, location ID/code/name, manufacturer lot, full expiry date, product/regulatory status, recorded on-hand, receipt and signed-correction units. Location `stock_status` remains **quarantine**; `dispensable_units` remains **0**, including for unexpired or active products. Expiry classification uses the outlet-local date at `as_of`; the labelled expiry date itself is included (`expires_on < local_date` is expired). This display convention is separate from release authority and is not an approved country-specific dispensing rule. No reserved, available, damaged, in-transit, financial valuation or approved stock-release value is inferred.

The UI holds one cutoff while inspecting a position and its movements. This is a **recorded-time view, not a durable cross-request database snapshot**: each aggregate is statement-consistent, but a transaction begun before the cutoff may commit later with an earlier `created_at` and appear on a later page/read. Product labels/status are current metadata, not historical reconstructions. Refresh explicitly for current data; formal period close or an immutable export needs a separately designed snapshot contract. Do not represent this report as stocktake or accounting-close evidence.

## Security, failures and capacity assumptions

Assets are outlet quantities, commercial product information and staff attribution. Threats include another tenant, a sibling outlet user and a revoked or overprivileged insider. Every read requires authenticated tenant identity, `pharmacy.stock.read`, the live pharmacy/outlet reader or editor grant, scoped object lookup and existing FORCE RLS. Tenant/actor identity comes from the verified session, not query parameters. Invisible/foreign objects and revoked grants return 404 without existence disclosure; an unavailable authorisation check fails closed with 503. No hospital/corporate access inheritance is introduced. Responses use `Cache-Control: no-store`; logs must exclude response bodies and personal or customer data.

Planning assumptions, **not measurements or benchmarks**: peak 20 read requests/second across the slice, approximately 2/second for a busy outlet; read:write ratio 100:1; 50-row typical responses budgeted at 64 KiB and 200-row responses at 256 KiB. At peak, typical response traffic is about 1.25 MiB/second. Assume 2 million movement rows at 12 months and 6 million at 36 months (3× cumulative volume); at an illustrative 400 bytes/row this is 0.8/2.4 GB before indexes and storage overhead. Proposed operating objectives are 99.9% monthly availability and p99 ≤500 ms, subject to load/query-plan verification; these are not achieved SLO claims.

PostgreSQL is critical: a failed read returns an explicit failure, never a successful zero balance or stale prior-scope rows. The UI must hide failed/stale results and offer retry, with clear loading, empty and invalid-filter states. Scope/filter changes reset the selected lot and pagination; keyboard navigation, focus/scroll to detail and narrow-screen table scrolling are acceptance requirements. Use existing indexes and inspect plans against representative volume before claiming the latency objective. No external RPC or new datastore is needed in the read path.

No new schema, stock master, movement kind or persisted balance projection is introduced. Existing immutable pharmacy tables remain authoritative; the computed location/lot bucket identifier is a read key, never an authorisation or master-data key. No new NATS/JetStream consumer, Temporal workflow or Valkey cache is added for these synchronous reads. Existing receiving outbox behaviour is retained. Future reservation timers, FEFO allocation, replenishment and cross-module handoffs belong to their owning stories. This adds no infrastructure resource; database read cost must be measured. Application rollback can remove the additive UI/read routes through normal GitOps without deleting inventory history; no migration is required.
