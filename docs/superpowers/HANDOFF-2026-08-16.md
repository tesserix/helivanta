## The architecture, in three lines

```
Zitadel  → who authenticated, and when          (knows nothing about hospitals)
HMS      → mints its own session: sub + tenant_id + auth_time
OpenFGA  → what they may do, resolved per request (no roles in the token, ever)
```

**The durable win is HMS owning its session, more than the vendor change.**
Before, the IdP's token *was* the session, so the IdP's model dictated tenancy,
revocation and switching. Now Zitadel answers one narrow question — which is
what makes the IdP swappable at all.

Key documents:

- `docs/adr/0006-zitadel-not-gip.md` — supersedes ADR-0002
- `docs/superpowers/specs/2026-08-15-zitadel-auth-design.md` — protocol (D1–D7, **D4a**)
- `docs/superpowers/specs/2026-08-15-zitadel-tenancy-topology-design.md` — topology (**D5a**)
- `docs/superpowers/spikes/2026-08-15-zitadel-*.md` — observed behaviour everything rests on

## Pending, in the order I would take them

### 1. #848 — no idle timeout *(highest real risk)*

A clinician who walks away without signing out leaves a valid HMS session
cookie, so the next person at the terminal is simply *in*, as them. `/login` is
never reached, so no `prompt` value can intervene. #847 fixed the explicit
sign-in paths and **does not** cover this.

Matters most for **#54's audit trail**: actions attributed to whoever the
session says they are. An inherited session means wrong attribution in a record
that is supposed to be evidence.

The trap when building it: **silent renewal must not count as activity**, or an
untouched tab renews itself forever and the timeout never fires — while
everything looks like it works.

### 2. #45 — secrets management *(blocks production)*

HMS became a credential issuer. The API refuses to boot without
`SESSION_SIGNING_KEY`, and only the dev-key path exists. Production cannot run
until this lands.

### 3. #54 — audit trail *(largest unstarted foundation piece)*

Still has **no milestone**. Gets more expensive per module that starts writing
PHI.

**Binding constraint from the topology spec (D4):** it must attribute actions to
an **HMS-owned identifier**, with the Zitadel `sub` as an attached credential —
not the key. This is not hypothetical: HMS changed identity providers this week,
and GIP subjects and Zitadel subjects are unrelated values. An audit trail keyed
on GIP subjects would be silently corrupt right now. Audit records cannot be
rewritten, so this is decided when #54 is designed or not at all.

### 4. Branded login *(cross-repo, not blocking)*

Credentials are typed on Zitadel's **stock** hosted login. Branding it means
composing `@tesserix/web`'s `AuthLayout`/`AuthCard` in the org's
`zitadel-login` aurora build — a different repo.

**Hard constraint (D5a):** the fields must keep the accessible names `Email`,
`Password`, and a button named `Sign in`. Rename them and all eleven e2e specs
fail at the login step simultaneously, looking like a broken application rather
than a renamed label.

**Open product question the user raised and has not decided:** whether HMS
should render the login form itself, calling Zitadel's Session API, so no
redirect is visible. It is possible and documented, and it costs: HMS would hold
an **`IAM_LOGIN_CLIENT`** instance-level credential on an instance shared with
every other Tesserix product, and would have to implement MFA, passkeys,
password-change-required, reset, lockout, and IdP handoff — the last being the
capability that justified Zitadel over GIP. My recommendation was to brand the
hosted page instead. **Not decided.**

## Things that will bite you if nobody says them

**The coverage gate is flaky under container load.** One run failed pharmacy
with a test taking 182s; re-running in isolation passed and the gate went green.
Same class as the closed #763. Do not chase it before re-running.

**`internal/bootstrap` sits at ~66%**, below the 70% floor, but is not in the
gate's `is_gated()` set. `V1Chain`, `RateLimitConfig` and `MountUnauthenticated`
all live there and are load-bearing.

**Zitadel's `zitadel` container reports `unhealthy` while serving fine.** Known
quirk, root cause undiagnosed, documented in the spike. Do not "fix" it by
loosening a probe.

**A 200 from Zitadel's user-creation API does not mean it did what you asked.**
`POST /management/v1/users/human` silently drops unrecognised JSON keys.
`passwordChangeRequired` exists only on the `_import` sibling. This is why the
seed script verifies every account by completing a real login rather than
checking a status code.

**Every `WITH CHECK` needs its own `NULLIF`.** An unset `app.tenant_id` GUC
returns `''`, not NULL, on a reused pooled connection, and `''::uuid` is a hard
error. `USING` clauses are safe because `hms_tenant_visible` carries it;
`WITH CHECK` cannot call that function (the lint forbids it) so it needs its
own. Without it the same cross-tenant write reports a clean RLS rejection or a
uuid syntax error depending on pool scheduling.

**GitHub Actions is blocked by an org billing error.** Jobs fail in seconds. All
verification is local; do not debug the red checks.

## How this work has been running, and why

Worth continuing, because it kept finding real defects:

- **One subagent per task**, reviewed independently before the next is
  dispatched — re-running its mutations rather than trusting the report.
- **Every assertion observed failing before it passes.** Roughly a dozen tests
  this session turned out not to discriminate; two agents caught their own, and
  two were mine.
- **A mutation that breaks nothing is a finding.** That is how the unmounted
  limiter, the vacuous SSO-clearance assertion and the `AadhaarID` hole in the
  PHI allowlist were all found.
- **Reports have contained factually wrong claims** — including mine. #841's
  original description asserted unauthenticated callers could exhaust OpenFGA;
  reading the handler disproved it. State what you checked; mark the rest
  unchecked.

Almost every defect this session was found by **running the thing**, not by
reading it. The fresh-clone bootstrap failures, the sign-out session bug, the
stale wording — none would have surfaced in review.
