## The one fact that determines everything: no image has ever been published

GHCR has no `helivanta-*` package under the user or under `tesserix`.
`.github/workflows/images.yml` has run and failed with `steps=0` and no
retrievable logs — the **Actions spending limit**. The job never starts.

Until that is fixed there is nothing to deploy, and the boot secrets, the
chart and the routing are all downstream of it. A manual `docker push` was
considered and **rejected by the product owner**: a hand-pushed image has no
Trivy gate, no SBOM, no signature and no provenance, and it would be the
artefact that ends up promoted.

## The four blockers, in order, all human-owned

### 1. Actions billing

Everything is downstream. Nothing an agent can do.

### 2. The two boot secrets (#45 Task 4)

Write via the `secret-service.tesserix.app` console — **not the `bao` CLI**,
which needs a port-forward and a human token OpenBao's Kubernetes auth is not
designed to issue.

```
Namespace: helivanta   Apps: helivanta-api   Secret name: session-signing-key
Namespace: helivanta   Apps: helivanta-api   Secret name: zitadel-login-client-token
```

**The app segment is `helivanta-api`, not `api`.** See "OpenBao paths" below.
Generate the signing key with `make secret-session-key` — it mints exactly the
format `SessionSigningKeySeed` accepts.

Then activation is one line: add `- helivanta-api.yaml` to
`argocd/prod/apps/helivanta/kustomization.yaml` (chart is drafted in
tesserix-k8s#411).

### 3. Zitadel app + login-client machine user on production

Production Zitadel has **no Helivanta app** — the dev one is created by
`scripts/lib/zitadel.mjs` at first boot. This mints
`NEXT_PUBLIC_ZITADEL_CLIENT_ID`, which **Next inlines at build time**, so it
must exist *before* the shell image is built, not after.

Carries #45's D2 open item: whether creating a machine user on the shared
production instance needs the platform team's sign-off. Confirm before
executing, not after. `docs/runbooks/secrets.md` has the steps.

### 4. Cloudflare: tunnel ingress + DNS

**Tunnel routing is NOT in git.** The live cloudflared runs
`tunnel run --token`, a remotely-managed tunnel whose rules live in
Cloudflare's API. Follow
`charts/infrastructure/cloudflared/CLOUDFLARE_SETUP_PROD.md`.

Tunnel `2b78323c-aa85-4b96-b703-c831357e7d33`, origin
`http://istio-ingressgateway.istio-ingress.svc.cluster.local:80`. Add
`helivanta.app` and `*.helivanta.app` before the wildcards, plus two proxied
CNAMEs to `<tunnel-id>.cfargotunnel.com`.

> **The configuration endpoint is a `PUT` that REPLACES the entire ingress
> array, and there are 25+ live rules across `tesserix.app` and `mark8ly.com`.**
> A PUT built from a partial list silently deletes every rule it omits, and the
> first symptom is another product 404ing. GET, modify, PUT the whole thing.

## Proven versus inferred — the distinction matters more than the list

**Proven, by mutation, against live systems:**

- `hms_app` is `rolbypassrls=false`, `rolsuper=false`. A table created by owner
  `helivanta` auto-grants it INSERT+SELECT; as `hms_app`, INSERT succeeds and
  DROP fails `must be owner of table`.
- The OpenBao grant is **bounded**: `kv/data/helivanta/scope-probe/denial`
  returns `403 permission denied`. The path *exists* — a canary was written and
  its whitelisting PR (tesserix-k8s#392) deliberately **left unmerged**. Do not
  merge it; merging creates the policy and destroys the negative control.
- NATS JetStream is enabled (queried, not assumed — a non-JS server still
  answers a Ping, so readiness would pass and the first publish would fail).
- OpenFGA survives a pod restart, so it is genuinely on Postgres, not `memory`.
- Cross-namespace traffic to Postgres is denied; in-namespace succeeds.
- `TRUSTED_PROXY_CIDRS` refuses boot when unset, `none` starts, and **removing
  the call site from `main.go` boots straight past** — that last one is what
  proves the guard is reached, which a unit test cannot.
- The API container honours SIGTERM with **exit code 0** (exec-form ENTRYPOINT,
  distroless, so the binary is PID 1).

**Inferred, and NOT yet confirmed:**

- **`TRUSTED_PROXY_CIDRS=10.20.0.0/16`.** The request path is
  `browser → Cloudflare edge → cloudflared POD (10.20.x) → istio-ingressgateway
  → app pod` — two in-cluster hops, because cloudflared runs inside the cluster.
  Nobody has read the actual `X-Forwarded-For` at an app pod. **Slice 1b Task 9
  exists to confirm or correct this**, and a forged-header burst must be shown
  *not* to buy a fresh token bucket.
- The Trivy gate has **never been watched rejecting anything**, and the Cosign
  signature has **never been verified** — both merged unproven, blocked on
  billing. By this repo's own standard a gate nobody has watched fail is not
  known to be a gate.

## Traps found today, each of which cost real time

**OpenBao paths are app-scoped and the app segment is not a free choice.** The
chart generates one policy per whitelisted app, scoped to
`kv/data/<namespace>/<app-name>/*`, and names policy and role
`app-<namespace>_<app-name>`. Helivanta's only whitelisted app is
`helivanta-api`, so the sole readable prefix is
`kv/data/helivanta/helivanta-api/*`. The runbook documented
`kv/data/helivanta/api/*` for a full day — unreadable by the pod, and nothing
fails at write time. Fixed in #873, which also removed a Task 4 step that would
have **widened** the grant with a hand-written policy.

**ESO's `remoteRef` needs `property:` as well as `key:`.** Without it the Vault
provider returns the whole KV payload, so the projected value is
`{"password":"..."}` — non-empty, `SecretSynced`, and unusable. A presence check
passes while the credential is broken.

**`external-secrets.io/v1` is not served on this cluster.** Use `v1beta1`.

**LimitRange derives `default.cpu` from `max.cpu`.** Omitting the key does not
mean "no CPU limit" — the API server fills it in from the max. `helm template`
and `kubectl get` disagree, and the stored object is the truth.

**ArgoCD serves *cached* manifest errors.** After slice 1a merged, the
app-of-apps still reported a stale `app path does not exist`, so it never
created one of its child Applications — while four siblings read `Synced`. A
hard refresh (`argocd.argoproj.io/refresh=hard`) cleared it. Always compare
`.status.sync.revision` against `origin/main`.

**`ct lint` requires a version bump for any MODIFIED existing chart**, and
yamllint caps lines at 200 characters. Both fail the whole lint job.

**Tunnel routing is not in git at all** (see blocker 4). `k8s/cluster/cloudflared/`
was a complete orphaned copy — ConfigMap, Deployment and ExternalSecret,
referenced by nothing, every fact in it stale. It caused an inert PR to be
merged before being deleted in tesserix-k8s#409.

Still true from before: leftover `next dev` processes holding ports;
`zitadel-login` latching a stale PAT (`docker restart helivanta-dev-zitadel-login-1`);
Zitadel core reporting `unhealthy` while OIDC discovery serves 200; BSD `sed`
silently ignoring `\b` (use `perl -pi -e`).

## How the real defects were actually found

Reviews caught genuine problems today — a missing security context, a wrong
grant, an over-specific assertion. But **every structural gap was found by
something downstream trying to use the artefact**, not by review, not by CI,
and not by reading:

| Gap | Found by |
|---|---|
| OpenBao paths unreadable | The operator pasting a path into the console |
| Orphaned cloudflared configmap | The post-merge check finding no such object |
| No migrate image | The chart author looking for an image to run |

All three were errors in **task briefs**, written confidently and reviewed
without anyone asking whether the thing they described existed. The habit that
would have caught all three: before writing a brief, ask *what consumes this,
and has that ever actually run?*

Related: subagents corrected the controller four times this session and were
right each time — including that `Config.User` is `65532` not `65532:65532`,
and that the `openfga` database is owned by `helivanta` rather than `openfga`.
