# Pagination contract — design

**Issue:** [#816](https://github.com/tesserix/hms/issues/816) — List endpoints
truncate silently.
**Status:** implemented 2026-08-14. Deviations from the approved design are
recorded inline below, each marked **Implemented as**.
**Related:** #774 (foundation audit, Tier 2), #666 (API design standards),
#710 (contract testing in CI).

---

## Problem

Every list endpoint returns `{"data": [...]}` with a hardcoded `LIMIT` and no
cursor. A caller cannot tell a truncated page from a complete one, and cannot
ask for the rest. Six endpoints truncate silently, verified in the code on
2026-08-13:

| Endpoint | Limit |
|---|---|
| `GET /v1/medicore/visits` | 100 |
| `GET /v1/pharmacy/dispenses` | 100 |
| `GET /v1/pharmacy/medications` | 100 |
| `GET /v1/lab/orders` | 100 |
| `GET /v1/reference/pings` | 100 |
| `GET /v1/iam/members` | 500 |

`GET /v1/iam/roles`, `/v1/iam/me/tenants` and `/v1/iam/me/permissions` are
collection-shaped but bounded by nature — a fixed role set, a person's
memberships, a resolved permission set — and are out of scope.

**Those three keep the bare `{"data": [...]}` shape and gain no `page` object.**
So the API deliberately has two collection shapes, and the distinction is
"unbounded by tenant data" versus "bounded by construction" rather than an
oversight. A client can tell them apart by the absence of `page`, and the arch
test's allowlist (D4) is the enumerated list of which is which — so adding a
fourth requires justifying it in the same place.

The clinical consequence is the point. A busy OPD ward with more than 100 open
visits shows exactly 100, unmarked. A nurse who does not see a patient concludes
the patient is not there. `/iam/members` at 500 is the same defect further away:
it governs who has access to a hospital, so a truncated view there is an
access-control blind spot rather than a UX annoyance.

This is also the cheapest it will ever be. Six endpoints today; the response
shape is already frozen into `@hms/api` and every panel, and every module
generated by `make new-module` inherits it. The cost grows with the module
count.

## Decisions

### D1 — Additive envelope: keep `data`, add a sibling `page`

```json
{
  "data": [ … ],
  "page": { "next_cursor": "eyJ0Ijoi…", "has_more": true }
}
```

Last page: `{"next_cursor": null, "has_more": false}`.

Every existing client keeps working because `data` is untouched, so the six
panels migrate independently rather than in a flag day. `has_more` is carried
explicitly rather than inferred from a null cursor, so "last page" is never a
guess about whether the cursor was omitted deliberately or by a bug.

*Rejected: a fully-specified replacement envelope* (`items` + `pagination`).
Cleaner naming, but a breaking change to six panels, the `@hms/api` types and
the E2E selectors in one commit — and the shape being already frozen is the
issue's central argument.

*Rejected: `Link` header only.* Maximally compatible and RFC 8288-correct, but
it splits the contract across body and headers and is easy for a client to
ignore entirely, which is the failure mode being fixed.

### D2 — Structured, unsigned cursor validated against the caller's tenant

`base64url({"t": tenant_id, "c": created_at, "i": id})`. On receipt,
`cursor.t` must equal the caller's tenant claim or the request is refused 400.

Tampering with the *position* is deliberately not defended against, because it
achieves nothing: forced RLS already bounds every query to the caller's own
tenant, so a hand-edited cursor can only reposition the caller within data they
can already read — the same thing a different `limit` would do. The tenant field
exists to catch reuse and misrouting, not to resist an attacker.

*Rejected: HMAC-signed cursor.* Unforgeable, and would matter if the cursor ever
carried something RLS does not bound. Today it costs a signing key in config and
a rotation story for a threat RLS already neutralises. Revisit if the payload
ever grows beyond position.

*Rejected: opaque server-side token.* Reveals nothing and can encode arbitrary
state, but adds a table or Redis on a read path, needs expiry and cleanup, and
turns a stateless GET into a stateful one.

### D3 — Keyset, never offset

```sql
WHERE (created_at, id) < ($c, $i)
ORDER BY created_at DESC, id DESC
LIMIT $limit + 1
```

`created_at` alone is **not unique**, so `id` is a required tiebreaker rather
than a refinement.

Offset is disqualified, not merely disfavoured. A ward's list changes while it
is read: with `OFFSET 50`, one insert before page 2 pushes a row from page 1
into page 2 (the client sees it twice) and one delete pulls a row up (the client
never sees it). Silently dropping a patient from a list is the defect this issue
exists to fix, reintroduced through the back door.

The keyset also **survives its own anchor being deleted**: the comparison is on
values, not on the row still existing, so `(created_at, id) < ($c, $i)` still
selects exactly the rows following that position. No special handling required.

### D4 — Compile-enforced list routes

A generic `platform.ListRoute[T]` whose handler signature takes pagination
params and returns `([]T, error)`. The platform layer owns the limit clamp, the
keyset, the `+1` probe, the cursor encode and the envelope. A handler cannot
forget any of them and cannot return a bare slice.

This mirrors the guarantee `*platform.Router`'s unexported gin group already
gives for permissions, and satisfies
`docs/standards/engineering-principles.md` §4's preference for "impossible to
express" over "documented convention".

`ListRoute` is for **collections only**. Single-item reads such as
`GET /v1/reference/pings/:id` stay on plain `g.GET`: they return one object, and
paginating a single row is meaningless.

**One hole the type system cannot close:** nothing stops someone registering a
collection through plain `g.GET`. An arch test forbids it, working from an
explicit allowlist of the non-paginated `g.GET` routes — the three bounded iam
routes plus single-item reads — so a new unpaginated collection fails CI and a
deliberate exception has to be written down next to the others. Stated here
rather than left implicit, because a design claiming compile-time enforcement
while leaving an unguarded path is worse than one that names the gap.

*Rejected: arch test only.* Much smaller change, but it catches the mistake
after it is written, and a test that walks handler bodies is more fragile than a
type signature.

*Rejected: typed helpers plus review.* Reads naturally and is least disruptive,
but §4 ranks documented convention last precisely because nothing stops the
seventh endpoint doing what the first six did.

### D5 — Default 50, max 200, reject anything larger

| Request | Result |
|---|---|
| `limit` absent | 50 |
| `limit` = 200 | 200 |
| `limit` = 201 | 400 `invalid_request` |
| `limit` = 0, negative, non-numeric | 400 `invalid_request` |

**No silent clamping.** Clamping teaches a client that `limit=5000` worked while
quietly returning 200; the client then paginates wrongly or assumes it has
everything — the same silent-truncation class this issue exists to end.

`/iam/members` drops from 500 to the same contract, gaining a cursor.

### D6 — The `+1` probe belongs in the platform layer

Fetching `limit+1` rows and trimming to `limit` answers `has_more` without a
second query. A `COUNT` would be slower and *wrong*: it races inserts between
the two queries.

Putting the probe in `ListRoute` means the trim and the flag are computed once
from one slice. A handler that returned `limit+1` rows to the client, or
reported `has_more` from a stale count, is not expressible.

## Architecture

Three units, each with one responsibility:

| Unit | Responsibility | Depends on |
|---|---|---|
| `pkg/pagination` | Cursor encode/decode/validate; `limit` parse and validate | nothing — no DB, no gin, no table knowledge |
| `platform.ListRoute[T]` | Route wrapper: parse params, call handler, `+1` probe, build envelope | `pkg/pagination`, `platform.Router` |
| `tenantdb` keyset helper | Applies the keyset predicate, ordering and `LIMIT n+1` to a GORM query | `pkg/pagination` |

Handlers shrink. `visits.list` currently does `WithTenant` → `Order` → `Limit` →
`Find` → `respond.OK`; it becomes a repository call returning `([]visit, error)`.

**No schema change and no migration.** All six tables already carry
`(tenant_id, id, created_at)` — checked individually rather than assumed — which
is what makes one shared keyset helper viable instead of six variants.

### Timestamp precision — the detail that breaks this if got wrong

Postgres `timestamptz` stores **microseconds**. If the cursor serialises
`created_at` at second or millisecond precision, every row sharing a truncated
timestamp with the anchor is skipped or repeated — and it fails *only* under
fast inserts, which is exactly when a ward is busy and nobody is watching.

The cursor must round-trip the full stored precision. T2 below is the dedicated
guard. This is the pagination equivalent of the `auth_time`-vs-`iat` trap in
#781: plausible-looking, passes casual testing, wrong under load.

## Migration

The additive envelope lets the backend land first and each panel follow
independently.

**The frontend work is not optional.** Today's screens show up to 100 rows (500
for members). With a default of 50, they show fewer unless the panels can fetch
the next page — shipping the backend alone takes a ward list from "silently
truncated at 100" to "silently truncated at 50", which is strictly worse.

Six panels need the affordance: `visit-panel`, `dispense-list`,
`medications-panel`, `order-list`, `ping-panel`, and the members list.

**"Load more", not infinite scroll.** The absence of the button is a positive
statement that the client has everything; it is keyboard-accessible by default
where infinite scroll needs work to be; and a clinician scrolling a ward list on
a tablet should not have the ground move under them.

`useApiQuery` is a thin `useQuery` wrapper, so `useInfiniteQuery` would normally
go there — but that changes the hook's contract for every consumer. A narrow
`useApiPagedQuery` is added beside it instead, leaving the hook every panel
already uses untouched.

**Implemented as** `useApiPagedQuery(key, path, opts: { poll?: boolean } = {})`.
The design did not mention `poll`, but `dispense-list` and `order-list` are
queue screens that `useApiQuery` was polling at `POLL_INTERVAL_MS`: moving them
to a hook without it would have traded silent truncation for a queue that stops
updating, which is a different regression rather than a fix. An infinite
query's refetch covers every page already fetched, so a clinician who has paged
past page one still sees live rows on everything in front of them.

**The generator matters as much as the six endpoints.** `make new-module` emits
a list endpoint; if the template still emits `g.GET` + `Limit(100)`, module seven
reintroduces the defect on day one and the contract is decorative. The template
moves to `ListRoute`, and the arch test keeps it there.

## Error handling

| Input | Response |
|---|---|
| `limit` absent | 50 |
| `limit` = 0, negative, non-numeric, or > 200 | 400 `invalid_request`, naming the valid range |
| `cursor` not base64url / not JSON / missing fields | 400 `invalid_request` |
| `cursor.t` ≠ caller's tenant | 400 `invalid_request` |
| DB failure | 500 via `respond.InternalErr`, cause logged against the request id |

Nothing is silently accepted, clamped or coerced.

On `docs/standards/engineering-principles.md` §3: the `limit` ceiling **is** a
capacity guard, but it is request validation rather than a limiter with a
backing store — there is nothing that can be "unavailable", so the fail-open
carve-out for capacity controls does not apply. Every invalid input is refused
rather than guessed at, which is the direction fail-closed points, and rejecting
is also the cheaper failure: a refused request costs one 400, while a guessed
one costs a client that believes it has all the data.

## Testing

Per `docs/standards/engineering-principles.md` §5, every assertion is proven able
to fail before it is trusted.

| ID | Test | Why it exists |
|---|---|---|
| T1 | Rows inserted mid-pagination → **every row exactly once** | The property offset cannot provide. Fails if the keyset is ever "simplified" to `OFFSET`. |
| T2 | Rows sharing a microsecond paginate exact-once | The precision trap. Fails only here, never in casual testing. **Implemented as** microsecond, not millisecond: Postgres `timestamptz` stores microseconds, so a millisecond-granular test would pass against an encoding that truncates the digit that actually exists. |
| T3 | The cursor's anchor row is deleted between pages | Proves the keyset is a value comparison, not a row lookup. |
| T4 | Exactly `limit` rows remain | `has_more` false, `next_cursor` null — distinguishable from a full page. |
| T5 | Empty collection | `[]` and no cursor, never `null` — the shape panels branch on. |
| T6 | A tenant-A cursor sent by tenant B | 400, asserted on the response, not on "it returned nothing". |
| T7 | `limit` = 0, −1, 201, `"abc"` | 400 each, with the range named. |
| T8 | Arch test: no collection route on plain `g.GET` | The one hole the type system cannot close. |
| T9 | Generator output uses `ListRoute` | Otherwise module seven reintroduces the defect. |
| T10 | Panel: "Load more" appends, and disappears at the end | Vitest with `renderWithProviders`, per the frontend standard. |
| T11 | E2E: a ward with more than one page reads to completion | End to end through the real stack, not an assertion about an envelope. **Implemented as** an exact page-size assertion (`toHaveCount(50)`) plus a walk to exhaustion, rather than only "the Load more button is visible". The dev database is shared and already held 71 visits, so a raised page size still leaves more than one page and the button visible — the button alone does not discriminate. The count does: it fails for any page size that is not the contract's. |

## Limitations

- **Cursors are position, not a snapshot.** A row edited between pages is
  returned with its new values; a row whose `created_at` changes moves. Neither
  is a defect for append-mostly clinical lists, and a snapshot would require
  server-side state (rejected in D2).
- **No total count.** `has_more` says whether more exists, not how much. A count
  on a tenant-scoped table under RLS is a full scan, and the screens this serves
  do not display one. Add it only when a screen genuinely needs it.
- **Ordering is fixed** at `created_at DESC, id DESC`. Sorting by other columns
  needs a cursor per sort key and is out of scope.
- **Six panels change page size from 100 to 50** and gain "Load more". Anyone
  relying on "the list shows everything up to 100" sees fewer rows and an
  explicit control instead.
- **A 50-row first page makes the e2e suite's shared hospital contended.**
  Every spec has its own login account but they all write into one tenant's
  rows, and `pagination.spec.ts` creates 55 visits. Run concurrently, that
  flood displaces another spec's freshly created patient off page one of the
  pharmacy queue. The bulk spec is therefore sequenced after the rest through
  a Playwright project dependency (`e2e/playwright.config.ts`) rather than
  isolated by data. Per-spec tenants would be the structural fix; it is a
  seeding change beyond this issue.

## Out of scope

- Filtering and sorting as a general contract — related and worth doing, but a
  separate decision surface. This fixes truncation.
- The wider API style guide (error envelope, versioning, OpenAPI) — #666.
- Contract testing in CI for the resulting shape — #710.
- Bulk export endpoints (streaming, resumability). None exist yet.
- Cursors on `/roles`, `/me/tenants`, `/me/permissions` — bounded by nature.
