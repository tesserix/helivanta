# Private organisation licence evidence

Owner: Supply module. Refs #1135/#1005, epic #1133, parent #979. Builds on released #1161 and ADR 0028. This slice delivers private evidence intake, scanning, release and access; independent dossier review remains the next separate acceptance gate. Neither clean evidence nor a declaration enables trading.

## Workflow and contract

Administrator, purchasing and compliance users with the current party role and evidence-write permission create an intent for a specific current licence version. A stable client UUIDv7 identifies the file. Input is only expected_licence_version, filename, content_type, size and SHA-256. The licence, party and tenant come from the verified request scope; hospital IDs, object keys, approval and scan results cannot be supplied. Only complete passive PNG/JPEG images up to 10 MiB are supported; PDF/active content requires a later safe-rendering design.

Under `/v1/supply/parties/{party}/licenses/{license}/evidence`: PUT `/{file}` creates/replays an exact intent; PUT `/{file}/content` accepts bounded raw bytes; GET lists with bounded keyset pagination; GET `/{file}/download` streams only clean released generations; POST `/{file}/retry/{attempt}` queues a new committed attempt from scan_error; POST `/{file}/revoke` makes a clean file unavailable without deleting history. Read permissions include administrator, purchasing, compliance, finance and auditor; writers exclude finance/auditor. Both route permission and a current object grant are required. Unknown/inaccessible scope is 404, malformed content 400, conflicting intent/version 409 and uncertain storage/processing dependency 503.

The screen lists filename, source licence version, upload time, safe lifecycle status, reason and actions. It uses the existing query/error/loading/dropdown conventions and accessible file selection. Retry keeps the original ID; list refresh reflects durable results. A file for an older licence version is labelled historical and is ineligible for a new current verification dossier. Authorised auditors can still download historical clean evidence; source edits invalidate verification eligibility, not immutable audit history.

## Data and security boundary

Additive `0003_supply` owns supply_license_evidence. Compound foreign keys bind tenant/party/licence/source-version to an immutable licence revision. Forced RLS pins exact tenant, party and principal, independent of hospital group visibility. Immutable metadata includes source version, filename, content hash/size/type, creator and timestamps; immutable provenance includes upload date and GCS generations. No hard delete/truncate path is exposed. Read/download/revoke/retry and state changes are audited without recording filenames, licence numbers or bytes in events/logs.

Opaque GCS keys: `t/{tenant}/o/organisation/{party}/r/{license}/d/{UTC server upload date}/f/{file}/v/1`; patient/staff paths stay unchanged and still require a hospital. Organisation scope rejects a hospital. Uniform private bucket access, public access prevention, generation preconditions and pinned generation downloads apply. Storage never runs while authorization/row locks are held. Recheck current grant and original licence version before committing uploaded bytes; a revocation/source edit during an upload cannot advance the record. Orphan quarantine bytes remain private and follow the reviewed retention policy.

A separate process, task queue, PostgreSQL login and GCP workload identity isolate Supply processing from clinical/HR evidence. Reuse attachments.GCS, ClamAV validation and passive-content inspection. Do not import Workforce domain types, share its worker credential, broaden its policies or add permissions to read HR tables. The worker has only scoped non-filename metadata SELECT, lifecycle-column UPDATE, restricted audit/outbox INSERT and no DDL/BYPASSRLS. Add role-specific RESTRICTIVE audit/outbox insert policies, so the Workforce migration's existing permissive policies cannot erase these restrictions. Restrict event/audit shapes to opaque references and bounded outcomes. API/system/other-worker credentials cannot construct the processor.

The Supply workload identity gets generation GET on organisation quarantine objects and GET/create on organisation released objects; it must not list buckets or read staff/patient object paths. Use distinct IAM principal and object-prefix conditions matching `/o/organisation/`, not the existing HR identity. Required network edges are PostgreSQL, Temporal, ClamAV and GCS; processing writes an outbox row and does not need direct NATS network credentials.

## Lifecycle and delivery semantics

`upload_pending -> scan_pending -> available | rejected | scan_error`; explicit bounded attempt retry changes scan_error to scan_pending; available may be revoked. Only the scoped worker records verdict/provenance or makes content available. Clean fresh definitions, exact source generation, passive content, digest/size and conditional released-copy checks are mandatory. Rejected/missing/infected/stale-definition/unknown-generation content is never downloadable. Expired intents cannot be completed. A licence edit after a completed upload leaves historical evidence retained; it cannot make that file valid for a changed source revision.

The content commit and minimized scan-request event share one PostgreSQL transaction. The NATS consumer validates a bounded exact envelope, then starts a Temporal workflow ID incorporating tenant/party/licence/file/attempt. Redelivery acknowledges only the same durable execution; mismatching duplicates fail closed. Reuse the existing durable-receipt mechanics through a shared infrastructure helper if extraction is warranted, preserving Workforce behaviour and its independent tests. Temporal history contains opaque IDs/attempt and safe outcomes only. Retry storage/scanner unavailability with bounded exponential backoff; non-retryable bad scope/integrity is sanitised. Conditional GCS copy and a final locked transition make retries safe after copy/commit ambiguity. JetStream/Temporal outage leaves durable pending work; it never implies successful scanning.

## Capacity, operations and recovery

Planning assumptions, not measurements: 1,000 tenants at 12 months and 5,000 at 36; five organisations × three licences × two files per tenant gives 30k/150k current files. At 0.5 MiB average, active released plus quarantine is about 30/150 GiB before retained replacements. Plan 500 uploads/day with short bursts of two/second; four bounded scan activities across two workers target ordinary clean completion <20 seconds. Alert on queue age >5 minutes, rejected/scan-error spikes, unavailable scanner and stale definitions. API p99 target <500 ms for metadata, 99.9% availability; upload/scan duration is separate. Validate throughput before raising concurrency. Use existing CNPG/NATS/Temporal/GCS/ClamAV, plus a small dedicated worker deployment; incremental capacity/storage cost estimate tens of dollars/month within the existing cluster, subject to measured use and retention.

PostgreSQL and its immutable rows are authoritative. Valkey is not an authorization/verdict cache. Backup metadata and both GCS generations under existing restore procedures. Source digests and generation provenance must survive restoration; a restored ambiguous file stays unavailable until reverified. Country retention/residency, tax/licence verification, encryption keys and document destruction remain reviewed policy, not hard-coded legal assumptions. No patient-level data is required for this supply-chain workflow.

Prepare CNPG managed role, OpenBao-backed ExternalSecret, dedicated workload identity/IAM, worker command, probes and network policies through owning GitOps repositories. No production principal/secret/migration/rollout is changed until the concrete infrastructure diff and tested app are approved. Do not merge an upload UI whose required production worker is absent. Roll back code while retaining immutable rows; no destructive down migration. Keep other workers and the existing two-instance CNPG configuration unchanged.
