# Pharmacy expected-tenant precondition

Story [#1237](https://github.com/tesserix/helivanta/issues/1237), inventory parent #162. Production acceptance for #1232 reproduced HTTP 200 when an optional expected-tenant header disagreed with the authenticated session. Session/RLS/outlet enforcement still selected only authorized records; this change adds stale-workspace rejection.

The verified principal selects the tenant. Preserve existing permission, live membership, outlet grants and forced RLS. After those route gates, reject an explicitly supplied `X-Helivanta-Expected-Tenant` value that is malformed, nil, repeated or mismatched with HTTP 409 `session_changed` and generic refresh guidance. Absent headers remain compatible. UUID representations accepted by the existing Supply contract (including URNs) remain accepted when they identify the actual session tenant. Explicit empty and comma-combined values are invalid. Never echo tenant IDs or header values in errors.

Use one pharmacy-owned principal helper for the catalogue/stock/payables scope and the registry, medication and dispense entry points. Protect the generic insights and static country-configuration handlers explicitly as well. The caller trace includes all stock reads/writes/CSV, access administration, catalogue history, safety reports, inventory audit, finance and settlement delegates. Avoid changing platform-wide auth or another module's behavior.

Rejected requests must contain no CSV/attachment, successful export audit, business audit/outbox event or state change. Existing requests without the header and valid matching requests retain their behavior, including identical idempotent writes. A header matching tenant A on a tenant-B session cannot select A; that stale request is rejected before pharmacy I/O. A matching tenant-B header still receives 404 for tenant-A objects. Anonymous/nonmember/permission denials retain the platform's earlier gate ordering.

This performs at most one fixed-format UUID parse at each existing principal boundary, with no database, cache or network call. It adds zero requests, stored bytes or infrastructure resources regardless of 12/36-month data volume. Workload, retention, availability and deadlines remain those of the current service; the added processing budget is under 1 ms at the existing request boundary (a design budget, not a benchmark claim). Current Postgres/authz/NATS/Valkey failure behavior is unchanged; rejected requests reach no business dependency. A new saga, queue, cache, schema or backfill provides no value for this synchronous precondition.

Use public HTTP-interface red→green tests against the real PostgreSQL application role. Exercise all declared pharmacy route families, optional/canonical/URN headers, malformed/empty/repeated values, both tenant principals, permission/grant denials and unchanged audit/outbox/state counts. Retain existing CSV cancellation and stale-response UI tests; no product UI change is planned. Run the required backend gates and a real local authenticated API walkthrough before review. No migration is needed; rollback is an application image. Specific approval and deployed verification precede issue closure.
