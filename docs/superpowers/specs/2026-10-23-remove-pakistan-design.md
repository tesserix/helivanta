# Remove Pakistan from the supported countries

Resolves #1287. Decided with the user: Pakistan is not a target market, so it is removed
entirely. Existing Pakistan records are **refused, not migrated**.

## Intent

The product is India first. Pakistan (`PK`, `PKR`, `Asia/Karachi`, `en-PK` / `ur-PK`) is a
supported country in `contracts/country-profiles.json`, so it appears in every country list:
outlets, supply parties, territories, deliveries and country policy. Choosing it creates
records the business will never serve.

Success:

- No country list offers Pakistan.
- No API accepts `PK` or `PKR`.
- No database table can hold a new Pakistan row.
- A database that already holds one stops at the migration with a clear message, rather
  than having it changed silently.

## Decisions

- **D1 The profile contract loses Pakistan.** Its generated outputs are regenerated:
  - `contracts/country-profiles.json` keeps India only. The Go output
    (`backend/pkg/countryprofile`) and the TS output (`packages/api/src/country-profiles.ts`)
    are regenerated by `scripts/generate-country-profiles.mjs`, never edited by hand.
  - The trading-policy contract and its generator (`scripts/generate-trading-policy.mjs`)
    drop every PK entry.
  - The supply and pharmacy contracts drop any PK value.
  - Every API that validates a country or currency against the profile then refuses `PK`
    and `PKR` with its existing 400.
  - Pharmacy's product, bill and payment currencies were checked only as three letters, so
    they would still accept `PKR`. They now accept only a supported country's currency,
    using a generated `countryprofile.SupportedCurrency`. _(Ruled while building.)_
    - The rule that a stocked product's currency cannot change is now unreachable, because
      there is no second currency to change to. It stays for when another country returns.
- **D2 Existing Pakistan rows are refused, not migrated (agreed).** Each owning module gets
  one new, append-only migration. It first counts that module's Pakistan rows across every
  tenant. If there are any, it raises an error naming each table and its row count, and it
  changes nothing. Only an empty database is tightened.
  - Fail closed: moving an outlet or party to India would silently change its currency,
    time zone, tax identifiers and regulatory rules, a decision no migration can make. An
    operator who finds rows deletes or corrects them deliberately, then re-runs.
  - **Rows counted:**
    - Pharmacy:
      - `pharmacy_outlets.country_code = 'PK'`;
      - `PKR` as the currency on catalogue products, payables, settlements and any other
        pharmacy table with a `currency` column.
    - Supply:
      - `country_code = 'PK'` on parties, addresses, identifiers, premises, licences,
        territories and delivery tasks;
      - identifier kinds `ntn` and `stn`.
    - Workspace country policy: `country = 'PK'` or `currency = 'PKR'`.
  - **The count must see every tenant.** Migrations run as the schema owner, and under
    `FORCE ROW LEVEL SECURITY` the owner sees no tenant's rows (#894).
    - This was checked on a scratch database with a non-superuser owner. Forced, the owner
      counted 0 of 1 Pakistan rows, so a plain count would wave every database through.
    - So each migration does the following inside its own transaction, for each table it
      counts:
      1. `ALTER TABLE … NO FORCE ROW LEVEL SECURITY`;
      2. count;
      3. `ALTER TABLE … FORCE ROW LEVEL SECURITY` again, before anything else.
    - `ALTER TABLE` holds an `ACCESS EXCLUSIVE` lock until the transaction ends, so no other
      session ever sees the table unforced. If the migration raises, the rollback restores
      the setting.
    - Tests run the migrations as the harness's real owner role, which is not a superuser.
      A test with one tenant's PK row must see the refusal. The test is proven able to fail
      by a plain count, which passes wrongly.
  - **Constraints after the count:**
    - Supply's `IN ('IN','PK')` checks become `= 'IN'`, and the identifier-kind check drops
      `ntn` / `stn`.
    - Workspace's country and currency checks become India only.
    - Pharmacy's `country_code` check stays a two-letter pattern, because pharmacy reads
      the country profile for its rules. Its new migration only refuses existing PK rows.
      _(My call: the API already refuses any code without a profile.)_
- **D3 Code paths for "no tax scheme" stay, and stay tested.** India has a tax scheme, so no
  supported outlet reaches them, but a record that predates a profile's removal still can.
  The server keeps failing closed there:
  - the overview has no Setup tile;
  - `tax=unclassified` is a 400;
  - tax registration is refused.

  Tests reach these paths with an outlet whose country has no profile, seeded directly in
  the database, as legacy data would be. They no longer use Pakistan. _(My call.)_

- **D4 Tests that use Pakistan as "the other country" are rewritten, not deleted.**
  - A check that refused a PK-only value (`ntn`, `PKR` at an Indian outlet) now proves
    that `PK` and `PKR` themselves are refused.
  - Cross-country isolation tests use an unsupported code and expect the refusal.
  - Frontend tests that defaulted Pakistan to PKR are replaced by a test that the
    country lists offer India only.
- **D5 Documentation is corrected in the same change.**
  - Current-state documents drop Pakistan: domain specs, the supply API doc, delivery
    notes and local testing guides.
  - The requirements document `pharmaconnect-india-pakistan.md` is renamed to India only,
    and its Pakistan sections are removed.
  - ADRs 0026, 0027 and 0030 are records of past decisions, so they are not rewritten. Each
    gets a dated "Superseded in part by #1287: Pakistan removed" note.
  - The two architecture diagrams that name Pakistan are updated, or else marked
    superseded if they cannot be regenerated. The builder decides which.

## Not covered

- Adding another country.
- Removing the multi-country machinery: profiles, per-country policy and timezone checks.
  It stays, with India as its one entry.
- Deleting or correcting anyone's Pakistan data. An operator does that, outside this
  change, if the migration refuses.

## Verification

- **Go:**
  - Each new migration fails, and leaves the schema unchanged, when one tenant holds a PK
    row (or a PKR document, or an `ntn` identifier). Its error names the table.
  - Each migration succeeds on a clean database, after which inserting `PK` is refused by
    the database itself.
  - The APIs that took a country refuse `PK` and `PKR` with 400.
  - The "no tax scheme" behaviours still hold for an outlet with no profile.
  - `go run ./cmd/contractdocs`, then `-check`.
- **Generators:** the country-profile and trading-policy generators' checks pass, and no
  generated file mentions PK.
- **Vitest:** no country select offers Pakistan.
- **Final grep:** `git grep -n -E '"PK"|PKR|Asia/Karachi|Pakistan'` is empty, apart from the
  ADR supersession notes and this spec.
- **Gates:** every gate, plus the full e2e suite on a production build.
