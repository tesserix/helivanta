# Supplier receiving and financial handoff

SupplyConnect owns consent/orders; the supplying stock owner is either SupplyConnect or PharmaConnect. The receiving pharmacy owns hospital custody, stock and its existing operational accounts. Link original supplier invoices to those existing accounts; do not create a second payable ledger or turn physical receipt into an invoice. External invoice issuance, statutory tax decisions and real provider settlement remain with their accountable owners.

Commercial receipt and invoice lineage is protected from other tenants, callers without financial/outlet authority and compromised clients. Browser, Global API, product authorization and purpose-bound database reads are separate trust boundaries. Caller-supplied IDs select records; they cannot supply authority.

## Verified implementation and change

Supplier receiving posts an attributable normal receipt movement whose ID is the supplier receipt ID. Existing payables enforce exact-outlet/currency receipt links, unique receipt costing, immutable bills, exact minor-unit amounts, credits, partial payments and external payment reversals. The current form requests all stock movements through a separate stock permission and gives finance no current correction, shipment or discrepancy context.

Add a bounded private accounts acquisition-receipt projection under the existing accounts-read permission plus current outlet reader authority. Return exact tenant/pharmacy/outlet, movement and immutable batch/catalogue currency/unit, existing payable link, and optional supplier lineage (order/shipment, source stock owner, original/effective accepted counts, current summary version, closed state and shortage/rejection). Read only Pharma-owned tables and retained source observations. A source ID is never authority. Expose no patient, Staff, counterparty private directory, invoice contents or source balance. Reads are audited. Current queries re-evaluate corrections/receiving state; absence, refusal or dependency failure cannot appear as successful reconciliation.

Use the projection in the bill form rather than the stock API. Only uncosted receipts in the selected document currency can be selected. Present original/effective quantities and unresolved receiving/discrepancy status; do not call a linked payable a successful three-way match. Preserve original invoice amounts and receipts when corrections happen. The existing inventory audit continues to report incomplete valuation when correction evidence prevents a reliable value. Existing finance permissions continue to gate bills, payments and adjustments; no operating duty receives financial permissions.

## Contract, recovery and scale

Canonical acquisition models live in contracts/pharmacy-accounts.json and generate owner Go and SDK Zod types. Signed keyset pages order by receipt creation/id, limit 50, bind current outlet/caller and explicitly validate expected workspace headers. SDK rejects foreign, duplicate, invalid continuation, incompatible linkage and inconsistent quantities. The receipt list is a current projection, not an authority snapshot or a commercial match certificate. Existing immutable bill command IDs and receipt GET support retained evidence; ambiguous bill save freezes the submitted input and recovers the exact original ID before any replacement attempt.

Reuse platform planning assumptions (50/150 tenants, 1,000/3,000 aggregate peak RPS, typical 2–20 KiB). Page size 50 bounds source JSON decoding; indexed movement/outlet, receipt, correction and payable links bound the query. No new service or datastore. Control-plane p99 <500 ms and 99.9% remain targets requiring measurement. Owner DB or authorization failure refuses the read; broker failure retains existing outbox work. Additive pharmacy migration 0043 adds a narrow SELECT-only financial acquisition purpose to three receiving evidence tables. The single permissive tenant policy remains; restrictive SELECT permits the new read purpose, while separate restrictive UPDATE/DELETE policies retain their original row predicates and the existing write checks remain unchanged. No stored row or legacy migration is changed. Rollback removes the new reader/UI without erasing financial or physical evidence.
