# Pharmacy tax setup: recognise a resent command — design

- **Issue:** #1715 (finding F-7, case SET-14 of the [counter acceptance plan](../../qa/2026-11-09-pharmacy-counter-acceptance-plan.md))
- **Date:** 2026-11-14
- **Status:** proposed

## Problem

An outlet GST registration and a product tax classification are each created
by a POST that carries no client identity
(`backend/internal/modules/pharmacy/tax_registrations.go`,
`tax_classifications.go`). The server cannot tell a resend from a new
decision:

- With a reason, a double submit or a retried request writes two rows. The
  second becomes a same-date "correction" of the first, and the history keeps
  both for good, because the tables are append-only.
- Without a reason, the second request gets
  `400 a correction for the same date needs a reason`
  (trigger `pharmacy_tax_correction_reason`, `tax.sql`). The row was in fact
  recorded, so the user is told to fix something that is not wrong.

The shell disables the button while a request is pending, but that does not
cover a lost response, a retry or a second tab.

## Goal

A tax setup command is recorded at most once. A resend of the same command
by the same person returns what was recorded and writes nothing. A different
command reusing its ID is refused.

## Decisions

### D1. The two POSTs become client-identified PUTs

| Before                                               | After                                                        |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| `POST …/outlets/{outlet}/tax-registrations`          | `PUT …/outlets/{outlet}/tax-registrations/{uuidv7}`          |
| `POST …/catalogue/products/{id}/tax-classifications` | `PUT …/catalogue/products/{id}/tax-classifications/{uuidv7}` |

The POST routes are removed. Their only consumer is the shell in this
repository, and there are no customers yet (user decision for #1672), so
nothing outside the repo depends on them. Permissions, bodies and the row
returned are unchanged. A path ID that is not a UUIDv7 gets 404, as every
pharmacy path ID does (`registryID`, `catalogueID`).

This follows the invoice profile (`PUT …/invoice-profile/{uuidv7}`,
`sale.go`), the existing pattern for an append-only outlet fact.

### D2. Replay is decided before anything else

Inside the write transaction, the handler first takes an advisory lock on
the command ID, then looks up the ID within the tenant:

1. **No row:** the request is validated and inserted exactly as today. This
   covers scope, outlet date, `effective_from` not before today, identifier
   format and the same-date reason rule. Response 201.
2. **A row with the same intent and recorder:** that row is returned with 200. Nothing is validated again and nothing is written. A resend the
   next day therefore still gets its row back, instead of a "before today"
   400 for a command that already succeeded.
3. **Any other row:** 409, with nothing written. This includes a different
   body, a different person, a different outlet or a different product.
   The message says the ID was already used with different details.

The replay lookup still runs after `pharmacyVisible` and the scope checks, so
a caller who cannot see the outlet gets the same 404 as today, never a
replayed row.

**Fail closed.** An ID that matches a row but cannot be proven to be the
same command is refused (409), never treated as a new command. The primary
key is `(tenant_id, outlet_id, id)`, so a used ID in another outlet would
otherwise be inserted as a second command. The lookup is therefore by
tenant and ID only. A silent replay of someone else's decision would
misattribute it.

### D3. The intent is a stored hash of the normalised command

A migration (`00NN_pharmacy_tax_command_identity`, the next free pharmacy ID
at merge time; codex has claimed 0047) adds a nullable `intent_sha256 text`
column to both tables.

- **Registration:** a SHA-256 over outlet, jurisdiction, normalised
  identifier, `effective_from` and reason.
- **Classification:** a SHA-256 over outlet, product, classification code,
  supply nature, `rate_ppm`, exemption basis, `effective_from` and reason.
- Fields are joined with `\x1f`, as the invoice profile does. An absent
  optional field and a blank one are different values: blanks are already
  refused before the hash.

The recorder is compared through the existing `recorded_by` column.

Rows written before this change have no hash. No ID can replay them, because
a NULL never matches (D2.3). Their IDs were generated by the server and were
never given to a client, so nobody can resend them anyway. The column stays
nullable for those rows only. A CHECK cannot tell old rows from new, so the
handler is the one writer that sets the hash, and a test asserts that every
row it writes carries one.

The immutability triggers fire on UPDATE, DELETE and TRUNCATE. `ADD COLUMN`
with no default rewrites nothing and fires none of them.

### D4. The shell keeps one ID per submitted command

Both forms (`tax-registration-panel.tsx`, `tax-classification.tsx`) hold a
command ID together with the values it was sent with:

- Submitting the same values as the last attempt reuses its ID. This covers
  a double click, a retry after an error, or a lost response.
- Submitting different values generates a new UUIDv7 with the existing
  `newPharmacyId()`. Changed values are a new decision, so they must not
  get the 409 meant for a reused ID.
- After a success the form resets, so the next submission starts a new
  command.

The API client paths in `packages/api` and the contract entries change to
the PUT routes. The input schemas, which are generated from
`contracts/pharmacy.json`, are unchanged because the body is unchanged.

### D5. Superseded docs are corrected in the same change

- `docs/api/domains/pharmacy.md`, tax setup row: the routes, replay and 409.
- The contract registry, regenerated with `go run ./cmd/contractdocs`.
- Acceptance plan: F-7 is marked done, and SET-14 expects one row with no
  error on a double submit.

## Not covered

- Other pharmacy POST commands. F-7 is limited to tax setup. Any similar
  finding elsewhere gets its own issue.
- Rows recorded before this change. They keep their history, and they have
  no hash (D3).
- GSTN verification, the composition scheme and e-invoicing (as in #1283).

## Tests

Every new assertion is first seen failing.

- **Registration replay:** the same ID and body are sent twice. Both
  answers carry the same row (201, then 200), and the table holds one row.
  This holds both with and without a reason. Without a reason the test is
  RED today (400); with a reason it is RED today (two rows).
- **Replay on a later day:** the clock moves past `effective_from`, and a
  replay still returns 200 with the row. Mutation: validate before the
  lookup.
- **Conflicts:** each of these gets 409 and leaves the row count unchanged:
  the same ID with a different identifier; a different recorder (a second
  owner); a different outlet. Mutation: compare only the hash, or only the
  recorder.
- **Concurrent sends:** two requests with the same ID run in parallel.
  Exactly one row results, and both get it. Mutation: remove the lock.
- **Every new row has a hash:** the stored `intent_sha256` is not null.
- **Classification:** the same cases, plus the same ID used for another
  product gets 409.
- **Shell:** a double submit sends two PUTs to the same path. An edit after
  an error sends a new ID. A success followed by a new entry sends a new
  ID. Tests use `renderWithProviders`.

`go test -race` on pharmacy, `go run ./cmd/contractdocs -check`,
`pnpm turbo lint type-check test build format:check`.
